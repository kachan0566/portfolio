# API仕様書の書き方

「何を書けばいいか」「どこまで書けば十分か」を、初心者向けに整理します。

## このプロジェクトでの使い分け

| 対象 | 書き方 | 例 |
| --- | --- | --- |
| **社内の Blade 画面**（フォーム・リダイレクト） | このファイルのテンプレート（JSON ではなくフォーム例） | [`purchases.patch-arrival-API.md`](purchases.patch-arrival-API.md) |
| **将来の工場向け JSON API** | OpenAPI または同テンプレートの JSON 版。着手用メモは [`memo/integration/factory-receiving.md`](../integration/factory-receiving.md) | 未作成（段階11で追加） |

社内画面用に OpenAPI は不要。工場連携を実装するときだけ、連携部分の仕様書を足す。

---

## 基本の型（テンプレート）

1つのAPIにつき、次の項目を書くと、だいたい十分です。

```markdown
# [API名]

## 概要
- 何ができるAPIか（1〜2文）

## エンドポイント
- URL: /purchases/{id}/arrival
- メソッド: PATCH
- 認証: 要 / 不要

## リクエスト
### パスパラメータ
| 名前 | 型 | 必須 | 説明 |

### ボディ
| 名前 | 型 | 必須 | 制約 | 説明 |

### 例
（実際に送るJSONやフォームの例）

## レスポンス
### 成功時
- ステータスコード: 200
- 返るデータの形

### エラー時
| コード | いつ | 内容 |

## ビジネスルール
- 発注種別によって保存先が変わる、など

## 備考
- 関連画面、変更履歴など
```

**最初はこの7ブロックだけ**でOKです。全部を最初から完璧に書く必要はありません。

---

## 各項目の書き方

### 1. 概要（1〜2文）

**悪い例：**
> 発注を更新するAPI

**良い例：**
> 発注一覧から、指定した発注の入荷予定日とメモを部分更新する。

「誰が」「何を」「どうするか」が伝わるように書きます。

---

### 2. エンドポイント

最低限、次の3つは書きます。

| 項目 | 例 |
|---|---|
| URL | `/purchases/{purchase_id}/arrival` |
| HTTPメソッド | `PATCH` |
| 認証 | ログイン必須（本番想定） |

`{purchase_id}` のような `{}` 部分は「ここに実際の値が入る」という意味です。

---

### 3. リクエスト

#### パスパラメータ（URLの中の値）

| 名前 | 型 | 必須 | 説明 | 例 |
|---|---|---|---|---|
| purchase_id | 整数 | はい | 発注ID | 12 |

#### ボディ（送るデータ）

| 名前 | 型 | 必須 | 制約 | 説明 |
|---|---|---|---|---|
| expected_arrival_date | 文字列 | いいえ | YYYY-MM-DD | 入荷予定日 |
| arrival_memo | 文字列 | いいえ | 最大500文字 | メモ |

**ポイント：**
- **必須か任意か**をはっきり書く
- **形式の制約**（日付形式、文字数など）を書く
- **例**を1つ入れる（これが一番伝わりやすい）

```json
{
  "expected_arrival_date": "2026-06-20",
  "arrival_memo": "染工場から連絡あり"
}
```

---

### 4. レスポンス

#### 成功時

```json
{
  "success": true,
  "data": {
    "purchase_id": 12,
    "expected_arrival_date": "2026-06-20",
    "arrival_memo": "染工場から連絡あり"
  },
  "message": "入荷予定を更新しました。"
}
```

#### エラー時（表にまとめる）

| コード | いつ | 返る内容 |
|---|---|---|
| 404 | 発注が存在しない | 「見つかりません」 |
| 422 | 日付形式が不正 | どの項目がダメか |
| 500 | サーバー障害 | 「しばらくして再試行」 |

**エラーは成功時と同じくらい大事**です。フロント担当が「エラー画面をどう出すか」を決められます。

---

### 5. ビジネスルール

コードを読まないとわからない部分を、日本語で書きます。

例（あなたのプロジェクト）：
- 製品発注 → 明細の `finish_date` を更新
- 糸・生機発注 → 発注の `due_date` を更新
- メモは常に `arrival_memo` に保存

ここを書いておくと、**「なぜこう動くのか」**が後からわかります。

---

## どこまで書けば十分か？

### 最初（MVP・最小限）

| 書く | 書かなくていい |
|---|---|
| URL・メソッド | 認証の詳細 |
| 送るデータと型 | レート制限 |
| 成功時の返り方 | 変更履歴 |
| 主なエラー（404, 422） | 全パターンのエラー例 |

**1 API = 半ページ〜1ページ** くらいで十分スタートできます。

### チーム開発・本番前

足す項目：
- 認証方法
- 権限（誰が使えるか）
- 全エラーパターン
- テストケース

### 外部連携・長期運用

さらに足す項目：
- バージョン管理（v1, v2）
- 非推奨（廃止予定）の告知
- 変更履歴
- レート制限・タイムアウト

---

## 書く順番（おすすめ）

1. **概要**を1文で書く
2. **リクエスト例**を書く（いちばんイメージしやすい）
3. **成功レスポンス例**を書く
4. 項目表（パラメータ・制約）を埋める
5. **エラー**と**ビジネスルール**を足す

「表から埋める」より、**例から書き始める**ほうが楽なことが多いです。

---

## よくあるミス

| ミス | 対策 |
|---|---|
| 必須/任意が曖昧 | 表の「必須」列を必ず書く |
| 日付形式が書いてない | `YYYY-MM-DD` のように例示 |
| エラーを書き忘れ | 404・422は最低限書く |
| 実装と違う | 実装後に仕様書も更新する |
| 長すぎて読まれない | 1 API = 1ページ目安 |

---

## あなたのプロジェクトでの進め方

今すぐ全部のAPIの仕様書を書く必要はありません。次の順がおすすめです。

1. **よく使う・複雑なAPIから1つ**（例：入荷予定更新、在庫割り当て）
2. 上のテンプレートで半ページ書く
3. テストを書くときに仕様書を見る
4. 実装と違ったら仕様書を直す

---

## まとめ

| 観点 | 答え |
|---|---|
| 何のため？ | みんなが同じルールで開発するため |
| 何を書く？ | URL・送受信データ・エラー・ルール |
| どこまで？ | 最初は半ページ、必要に応じて増やす |
| どう書く？ | 例（JSON）から始めるのが楽 |

特定のAPI（在庫割り当てなど）を、このテンプレートで一緒に埋めていくこともできます。




# API仕様書の書き方（用語の説明つき）

API仕様書は、**「この窓口はこう使ってね」と決めたことを文章にしたもの**です。  
ここでは、仕様書に出てくる用語の意味と、書き方を一緒に説明します。

---

## まず全体像

ブラウザやアプリがサーバーにお願いするとき、だいたい次の流れです。

```mermaid
ブラウザ → 【エンドポイント】に 【リクエスト】を送る
                ↓
           サーバーが処理
                ↓
         【レスポンス】が返る
```

| 用語 | 意味（かんたんに） |
|---|---|
| **リクエスト** | サーバーへの「お願い」 |
| **レスポンス** | サーバーからの「返事・結果」 |
| **エンドポイント** | お願いを送る「窓口（住所＋やり方）」 |

---

## 用語解説

### 1. エンドポイント（Endpoint）

**APIの入口・窓口**のことです。「どのURLに」「どんな方法で」アクセスするか、のセットです。

例（あなたのプロジェクト）：
```
PATCH /purchases/12/arrival
```

| 部分 | 意味 |
|---|---|
| `PATCH` | やり方（一部だけ更新する） |
| `/purchases/12/arrival` | 住所（URL） |

レストランでいうと、**「厨房の入荷担当窓口に、変更の依頼を出す」** という感じです。

---

### 2. URL（ユーアールエル）

インターネット上の**住所**です。

```
https://example.com/purchases/12/arrival
│                    │
│                    └─ パス（どの機能か）
└─ ドメイン（どのサーバーか）
```

仕様書では、多くの場合ドメインは省略して `/purchases/12/arrival` だけ書きます。

---

### 3. HTTPメソッド（やり方・動詞）

同じURLでも、**何をしたいか**で使うメソッドが変わります。

| メソッド | 意味 | 例え |
|---|---|---|
| **GET** | 見る・取得する | メニューを見る |
| **POST** | 新しく作る・送る | 新規注文する |
| **PUT** | 全体を置き換える | 注文内容を全部書き直す |
| **PATCH** | 一部だけ直す | 入荷予定日だけ変更する |
| **DELETE** | 削除する | 注文をキャンセルする |

あなたのプロジェクトの入荷予定更新は **PATCH** です。日付とメモだけ変えて、発注全体は作り直していません。

---

### 4. パスパラメータ（Path Parameter）

URLの**中に埋め込まれた値**です。`{ }` で囲んで書くことが多いです。

```
/purchases/{purchase_id}/arrival
           ↑
      ここがパスパラメータ
```

| 名前 | 実際のURL例 | 意味 |
|---|---|---|
| `purchase_id` | `/purchases/12/arrival` | 発注IDが `12` |

**「どの発注を更新するか」** をURLで指定しています。

---

### 5. クエリパラメータ（Query Parameter）

URLの**末尾に `?` 以降で付ける値**です。検索や絞り込みによく使います。

```
/purchases?status=未入荷&due_from=2026-06-01
           ↑
      クエリパラメータ
```

| 名前 | 値 | 意味 |
|---|---|---|
| `status` | `未入荷` | 状態で絞る |
| `due_from` | `2026-06-01` | この日以降で絞る |

パスパラメータは「どれか1件を指定」、クエリパラメータは「条件で絞る」と覚えるとわかりやすいです。

---

### 6. リクエストボディ（Body）

お願いと一緒に送る**データ本体**です。フォームやJSONで送ります。

```json
{
  "expected_arrival_date": "2026-06-20",
  "arrival_memo": "染工場から連絡あり"
}
```

| フィールド名 | 送るデータの項目名 |
|---|---|
| `expected_arrival_date` | 入荷予定日 |
| `arrival_memo` | メモ |

GET（見るだけ）のときは、通常ボディは送りません。

---

### 7. レスポンス（Response）

サーバーから返ってくる**結果**です。

| 種類 | 内容 |
|---|---|
| **ステータスコード** | 成功したか・エラーか（数字） |
| **ボディ** | 実際のデータ（JSONやHTMLなど） |

#### ステータスコード（よく使うもの）

| コード | 意味 | いつ |
|---|---|---|
| **200** | 成功 | 処理がうまくいった |
| **302** | 別のページへ移動 | Webアプリで画面を返すとき |
| **404** | 見つからない | 発注IDが存在しない |
| **422** | 入力ミス | 日付形式がおかしいなど |
| **500** | サーバー側の障害 | 予期しないエラー |

---

### 8. 認証（Authentication）

**「誰がアクセスしているか」を確認する仕組み**です。

- ログインしているか
- APIキー（合言葉のようなもの）を持っているか

本番では、誰でも触れるAPIにしないことが多いです。

---

### 9. バリデーション（入力チェック）

送られてきたデータが**ルールどおりか確認する**ことです。

例：
- 日付は `2026-06-20` の形か
- メモは500文字以内か

ダメなときは **422** を返します。

---

### 10. ビジネスルール

技術的な形式は正しくても、**業務の決まり**で処理が変わる部分です。

あなたのプロジェクトの例：
- 製品発注 → 明細の完了日を更新
- 糸・生機発注 → 発注の納期を更新

仕様書に書いておくと、「なぜこう動くのか」が後からわかります。

---

## 仕様書テンプレート（用語つき）

以下を1つのAPIにつき書くと、だいたい十分です。

---

### 【API名】発注入荷予定 更新

#### 概要
指定した発注の入荷予定日とメモを、一部だけ更新する。

#### エンドポイント

| 項目 | 内容 |
|---|---|
| URL | `/purchases/{purchase_id}/arrival` |
| HTTPメソッド | `PATCH` |
| 認証 | なし（本番ではログイン必須想定） |

#### パスパラメータ

URLの中に入れる値です。

| 名前 | 型 | 必須 | 説明 | 例 |
|---|---|---|---|---|
| purchase_id | 整数 | はい | 更新する発注のID | `12` |

#### リクエストボディ

一緒に送るデータです。

| 名前 | 型 | 必須 | 制約 | 説明 |
|---|---|---|---|---|
| expected_arrival_date | 文字列 | いいえ | `YYYY-MM-DD` 形式 | 入荷予定日 |
| arrival_memo | 文字列 | いいえ | 最大500文字 | メモ |

**送信例：**
```json
{
  "expected_arrival_date": "2026-06-20",
  "arrival_memo": "染工場から連絡あり"
}
```

#### レスポンス

##### 成功時（JSON API版の例）

```json
{
  "success": true,
  "data": {
    "purchase_id": 12,
    "expected_arrival_date": "2026-06-20",
    "arrival_memo": "染工場から連絡あり"
  },
  "message": "入荷予定を更新しました。"
}
```

| ステータスコード | 意味 |
|---|---|
| 200 | 成功（JSONを返す場合） |
| 302 | 成功（画面に移動する場合・今の実装） |

##### エラー時

| コード | いつ | 内容 |
|---|---|---|
| 404 | 発注IDが存在しない | 「見つかりません」 |
| 422 | 日付形式不正・メモが長すぎる | どの項目がダメか |
| 500 | サーバー障害 | 「しばらくして再試行」 |

#### ビジネスルール

| 発注種別 | 日付の保存先 |
|---|---|
| 製品発注 | 明細の完了日 |
| 糸・生機発注 | 発注の納期 |
| 共通 | メモは発注のメモ欄に保存 |

## 用語の関係（図）

1回のAPI通信を、部品に分けるとこうなります。

```
PATCH  https://example.com/purchases/12/arrival?status=未入荷
│      │                      │    │              │
│      │                      │    │              └─ クエリパラメータ（任意）
│      │                      │    └─ パスパラメータ（必須の指定）
│      │                      └─ パス（機能の場所）
│      └─ ドメイン（サーバー）
└─ HTTPメソッド（やり方）

＋ リクエストボディ（別途送るデータ）
  {
    "expected_arrival_date": "2026-06-20",
    "arrival_memo": "..."
  }

↓ サーバーが処理

レスポンス
  ステータスコード: 200 / 302 / 404 / 422 ...
  ボディ: JSON または HTML画面
```

## どこまで書けばいい？

| 段階 | 書くこと |
|---|---|
| **最初** | エンドポイント、パスパラメータ、ボディ、成功・主なエラー |
| **チーム開発** | 認証、権限、ビジネスルール、テストケース |
| **外部連携** | バージョン、変更履歴、レート制限 |

**1 API = 半ページ〜1ページ** から始めれば十分です。

---

## まとめ

| 用語 | 一言で |
|---|---|
| **エンドポイント** | APIの窓口（URL＋メソッド） |
| **URL** | サーバー上の住所 |
| **HTTPメソッド** | やり方（見る・作る・直す・消す） |
| **パスパラメータ** | URLの中の値（どの1件か） |
| **クエリパラメータ** | URL末尾の条件（絞り込み） |
| **リクエストボディ** | 一緒に送るデータ |
| **レスポンス** | サーバーからの返事 |
| **ステータスコード** | 成功かエラーかの数字 |
| **認証** | 誰が使っているかの確認 |
| **バリデーション** | 入力データのチェック |
| **ビジネスルール** | 業務上の決まり |

用語がわかったら、次は別のAPI（在庫割り当てなど）でも同じ型で書けます。特定のAPIを一緒に埋めていきたい場合は、どれか指定してもらえれば対応できます。
